## 本周用户流程

校园推荐列表 → 按校区/活动场景筛选 → 查看地点详情、推荐理由和文字方位 → 自行前往 → 点击“我已到达，完成打卡” → 服务器确认后显示本人完成状态和历史。

- 浏览不要求登录；提交和查看本人打卡记录需要微信登录。登录后返回原地点，不能把登录直接算作完成。
- 手动打卡记录用户自报完成，不显示“定位验证到场”。不接地图SDK、不调用位置权限或原生导航，不收集经纬度、轨迹、照片或照片位置信息。
- 本周不做拍照上传、相册选择、图片审核或公开照片展示。后续风景照片打卡另立需求，先确认权限、文件归属、展示范围、导出与清理；不能提前开启上传。
- 推荐基于负责人维护的校区、场景、地点资料，不读取私人日记正文推断偏好；不按GPS附近距离排序，不做公开到访榜或他人打卡查询。
- 收藏、纠错和支持资源保留原范围，排在基本推荐打卡之后，不作为本周基本链路的前置条件。固定模拟校园天气保留原标识。

## 契约与数据边界

现有公开campus.listPlaces/getPlace、任务tasks.transition/history只提供复用基础。目前没有已确认的地点打卡写入协议；本次不新增假action、不向旧payload直接塞placeId，也不修改数据库或生产开关。

Junhan与Jiawei、Qizhen Chen、Xiang Yu提交同一契约PR，Xiang Hong复核后实现，须明确：地点与一次到访的关联、重复打卡规则、稳定请求ID、完成状态/服务器时间、历史分页、地点失效、账号停用、源修订和导出清理。建议本周先按“同账号、同地点、北京时间同日只记一次”评审；重复点击/超时重试必须复用原请求，不能产生两条。该建议需在契约中落实，不能当成已有后端保证。

完成记录仅归本人，所有者取可信服务端账号；不把身份证明、私人历史、完成回执放到分享参数。成功前显示处理中，失败保留原操作，未知结果提供原请求重试。切号立即清空前一账号状态并丢弃旧响应，停用后拒绝新增。打卡须进入实际完整导出和注销清理；不得因复用任务模块就跳过来源修订或误删共享地点。

4. 重复点击、超时后重试、断网及恢复无重复完成；失败不显示成功，失效地点明确提示。
5. 游客、A/B切号、停用账号、迟到响应均有检查；公共推荐不返回私人记录，个人历史不能跨账号读取。
