# H04 任务换号恢复与旧操作退出

2026-11-03，Xiang Hong续作，基线main / 124dcd9f445094bd6cbf6590975d3d2fd6832484（PR #106），跟踪#98/#38。沿用现有客户端会话和任务协议，不改服务端或开放校园打卡。

## 触发与根因

A选择任务，网络响应尚未返回或已经出现未知结果；随后退出并登录B。原会话订阅虽然清空了页面，却保留控制器内部busy/pending/pendingScope，B的重新读取和重试都被A的旧操作挡住。旧操作finally还会无条件释放busy，并按旧绑定清空输出；即使仅解决阻塞，A的迟到结束仍会清掉B的新操作或页面。

新增7项中6项在基线失败，同绑定隐藏/返回原请求重试的对照用例通过。局部先清旧pending后，B能够读取，但5项仍因旧finally干扰失败，说明需要同时隔离操作的结束处理。对应红灯日志分别留test-results/2026-11-03-task-session-red.log与2026-11-03-task-session-late-red.log。

## 修复

modules/tasks/cloud.js在账号绑定变化时退休旧写入：清除旧账号内存pending、busy和待刷新标记，立即允许新绑定重新读取；新绑定不重放旧请求。每次写入标记独立代次，旧账号响应的结束处理不再释放或清空新账号的操作。卸载同样使旧操作失效。

这不撤销已经发送到服务器的A操作，也不声称失败等于未保存。返回A的新绑定需要重新读取服务器状态；服务器原请求回执、幂等与停用检查保持。同一个绑定内的断网、隐藏和返回仍保留原requestId/payload重试，不能将不同账号的旧请求交给新账号。
