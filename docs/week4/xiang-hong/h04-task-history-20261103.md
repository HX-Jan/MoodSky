## 已复现的问题

modules/tasks/cloud.js原来调用api.history()没有参数，service将空payload交给tasks.history；实际services/tasks-candidate.js明确要求from/to，生产backend只是投影entries为items，没有补日期。因此真实调用链会返回INVALID_INPUT，原客户端单元替身始终返回items，未覆盖这个接缝。此外控制器与Page忽略nextCursor，没有继续读取入口，即使首屏成功也无法读取后续记录。

首批10项回归在基线均失败。第一项实际连接客户端控制器、生产入口和锁定SDK离线数据库，43条本人合成记录因缺日期而读出0条；不是声称线上已发生私人数据丢失，也没有派发真实云请求。

## 本次修复

- 读取历史时以共享businessDate计算北京时间当天，提交含首尾的最近90天from/to；使用现有后端白名单，不改API、数据库或日期上限。
- 保存当前查询窗口与不透明游标，按服务默认20条分页；Page提供“加载更多历史”。同一次查询跨午夜仍沿用原窗口，重新读取才开始新窗口。游标只留控制器内存，不进入页面数据、分享或本机持久化。
- 加载更多失败保留已确认记录，重试同一冻结日期/游标查询；重复点击只发一次。相同任务/业务日期不重复追加，刷新丢弃旧分页响应。无效、循环或截断的后续响应不部分追加，也不假称已到末尾。
- 切号、隐藏、卸载、登录失效及停用清空已读私人历史、分页和游标；旧账号或旧查询的迟到结果不能回填。现有未知写入仍保留原requestId和payload，本次未改任务状态转换。
- 只复用既有tasks.history，不定义地点关联或把普通任务历史当作校园到访历史。校园手动打卡、实际地点、正式任务模板与共同验收仍待原负责人交付。
