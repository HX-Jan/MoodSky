## 2. 公共约定

所有请求使用 `{ apiVersion, requestId, action, payload }`，`apiVersion` 为字符串 `"1"`。`requestId` 为 8—80 个字母、数字、下划线或短横线；由现有请求封装生成，是去重标识，不是登录凭证。同一次不确定结果的重试保留原请求对象、原 ID 及原输入。

成功响应沿用 `{ apiVersion, requestId, ok: true, data }`；失败沿用 `{ apiVersion, requestId, ok: false, error: { code, message } }`。无有效请求 ID 时，失败响应中的 `requestId` 为 `null`。本稿不新增 `error.reason`、`latestVersion` 或隐藏的成功标志。前端封装成功时返回完整响应，页面读取 `result.data`；失败时抛出 `AppError`，页面保留输入并显示错误。

三个入口都使用服务器可信上下文解析的 active 账号，并仅操作该账号的记录。数据库 `ownerId` 由服务器填写；客户端不能提交 `ownerId`、`openid`、`uid` 或角色来指定本人或他人。现有外层校验已拒绝 `ownerId/owner/openid/OPENID/role/roles/accountId`；`uid` 在保存字段白名单处拒绝，查询和删除的完整白名单需后续补上。请求中的额外业务字段一律不用于授权。

`date` 为真实的 `YYYY-MM-DD` 业务日期，按 `Asia/Shanghai` 判定今天；`createdAt`、`updatedAt` 拟采用 UTC ISO 时间戳。服务端决定当前时间，客户端提交的时间不改变新建范围。天气码沿用 `SUNNY`、`PARTLY_CLOUDY`、`CLOUDY`、`RAINY`、`STORMY`；标签沿用 `STUDY`、`REST`、`EXERCISE`、`SOCIAL`、`ALONE_TIME`、`ANTICIPATION`、`TIREDNESS`、`CALM`。

## 3. 三个入口的拟约定

### 3.1 journal.upsert：新建或编辑

| 字段            | 必填 | 规则                                                                     |
| --------------- | ---- | ------------------------------------------------------------------------ |
| date            | 是   | 真实业务日期；新建仅今天及此前 29 天，编辑本人已有旧记录不受新建窗口限制 |
| weather         | 是   | 五种共享天气码之一                                                       |
| tags            | 否   | 缺省 `[]`；最多 5 个不同的固定标签；`null` 无效                          |
| text            | 否   | 缺省 `""`；最多 1000 个 Unicode 码点；允许空正文；`null` 无效            |
| expectedVersion | 是   | 非负整数；新建传 `0`，编辑传最近读取的当前版本                           |

这是完整保存输入，不是部分字段补丁。编辑时省略 `tags/text` 也会按现有校验变为空数组/空字符串，因此表单须携带用户希望保留的完整内容。正文不自动去掉首尾空格；码点计数复用 `Array.from(text).length`，不等同于屏幕上可见字符数。现有版本校验为 `Number.isInteger`，尚未限制安全整数范围；客户端应直接沿用服务端返回的版本，安全范围由 H03 与 Xiang Yu 确认。

拟返回 `data: { entry: JournalEntryView }`：

- 首次新建版本为 `1`。同一账号、同一日期最多一条有效记录；该日期已有记录而仍传 `expectedVersion: 0` 时返回 `CONFLICT`，不能静默改为编辑。
- 编辑仅在当前版本等于 `expectedVersion` 时成功，版本加一，保留原 `id/createdAt`，更新 `updatedAt`。同样正文但使用新 ID 发起的编辑仍是一项新操作，成功时版本加一。
- 传正版本但本人记录不存在时返回 `CONFLICT`，不能自动变成新建。旧记录可以编辑；窗口外没有记录的日期仍不能新建。
- 相同请求的重试不新增记录、不再次增加版本，具体规则见第 5 节。

### 3.2 journal.get：读取本人的某日记录

拟只允许 `payload: { date }`；必填真实日期，不接受记录 ID 或账号字段。拟返回 `data: { entry: JournalEntryView | null }`。

本人该日没有有效记录时返回 `entry: null`，包括已删除日期；不新增 `NOT_FOUND` 错误。查询不受新建窗口限制，窗口外真实日期可读已有记录，真实的未来日期在无记录时也是空结果。另一个账号同日有记录不能改变本人的空结果，也不暴露他人记录是否存在。

### 3.3 journal.delete：删除本人当前版本

拟只允许 `payload: { date, expectedVersion }`；日期真实，版本为正整数。删除表单先读取记录，再携带该记录的当前版本；不接受 `expectedVersion: 0`。

拟返回 `data: { date, deleted: boolean }`：

- 本人记录存在且版本匹配：删除成功，返回 `deleted: true`。后续查询不再返回该记录；回顾、装饰关联与未领取导出的失效要求交 H03 设计。
- 本人记录存在但版本已变化：返回 `CONFLICT`，保留最新记录，避免删除另一设备刚编辑的内容。
- 本人该日无有效记录：返回 `deleted: false`，表示当前没有可删记录；不确认他人是否有记录，不删除任何记录。仍需保留必要的无正文去重元数据，防止原请求重试时删除后来新建的记录。
- 删除不受新建窗口限制。窗口外旧记录删除后，不能以“重新新建”绕过 30 天窗口。

以上成功仅指已达到约定的业务不可读及关联失效条件，不把物理清除、备份处理或时限目标写成已完成；原子边界和失败恢复在 H03 确认。

## 5. 重复请求、竞争和删除后的约定

以下是 H02 要确认的外部行为；处理顺序、事务能力、回执状态和故障恢复交 H03。现有唯一索引已登记，但索引存在不能证明这些场景通过。

| 情况                                                 | 拟约定行为                                                           | 客户端处理                                          |
| ---------------------------------------------------- | -------------------------------------------------------------------- | --------------------------------------------------- |
| 两个不同 ID 同时新建本人同日记录                     | 至多一个成功；另一请求 `CONFLICT`，不覆盖赢家                        | 重新读取，由用户决定是否编辑                        |
| 两个不同 ID 携带同一旧版本编辑                       | 至多一个成功；另一请求 `CONFLICT`                                    | 保留本地输入，重新读取并提示比较                    |
| 同一账号、action、ID，输入相同；原成功保存版本仍有效 | 重放原成功结果，版本不增加；回执不复制私人正文                       | 可结束保存并刷新                                    |
| 同一账号、action、ID，输入不同                       | `CONFLICT`，不执行第二次写入                                         | 提示原请求不能更改；确认新操作后才能生成新 ID       |
| 原保存成功后跨过午夜，日期从第 29 天变为第 30 天     | 在有效回执内仍按原操作重试，不重新当作窗口外新建                     | 重试原对象，不改日期或 ID                           |
| 原保存后记录又被编辑或删除，再重试旧保存请求         | 拟返回 `CONFLICT` 并要求重读，不恢复已删除记录，不返回旧正文         | 保留输入并读取当前状态，不显示旧保存结果            |
| 删除已经成功且有效回执仍在，重试原删除请求           | 重放原 `deleted: true`，不再次删除；即使后来同日重建也不能删掉新记录 | 结束原操作，重新读取当前状态                        |
| 删除后同日重新新建                                   | 日期仍在窗口内才允许；须阻止删除前的旧版本编辑覆盖新记录             | 先读取；确认新建时使用新 ID 和 `expectedVersion: 0` |
| 重试时账号已停用                                     | 仍先执行 active 门禁，返回 `ACCOUNT_DISABLED`                        | 不凭旧回执恢复业务访问                              |

原删除返回 `deleted: false` 也需绑定回执；有效回执内重复原请求仍返回 `false`，不能因后来同日出现新记录就执行删除。回执有效期及过期处理在 H03 确认。

为防止“删除 → 重建 → 旧编辑覆盖”的版本碰撞，拟保留同一账号/日期的无正文版本或代际元数据，使重新新建不重用旧版本。首次创建为 `1`；重建版本不承诺重置为 `1`。该提案尚未验证数据库可行性，由 Xiang Yu 在 H03 复核，不能仅靠递增字段声称并发安全。

去重键沿用集合设计的 `(ownerId, action, requestId)`。回执保存输入摘要及必要的操作元数据，不复制正文。输入摘要的规范化方式、标签顺序是否影响摘要、回执有效期、请求执行中状态和过期后的处理尚待 H03 定义；本稿不承诺任意时间都能安全重放。删除后如何封锁回顾旧缓存、解除装饰引用和撤销旧导出也待 H03 设计与验证。

保存中禁止重复提交。网络失败可能意味着“服务端已经写入，但客户端没有收到”，因此保留生成过的完整请求对象，用户重试时传给 `submit(request)`。结果不确定时不重新调用 `createSaveRequest` 或当前 `remove(input)`，也不让用户改完输入后继续用旧 ID。当前封装没有自动重试；本步不修改界面或 service。

## 6. 错误约定

| 错误码                                                  | 触发条件及当前状态                                                    | 页面处理                                                       |
| ------------------------------------------------------- | --------------------------------------------------------------------- | -------------------------------------------------------------- |
| INVALID_REQUEST                                         | 外层格式、ID 或禁用身份字段错误；已有校验                             | 修正请求，不重复原非法请求                                     |
| API_VERSION_UNSUPPORTED / ACTION_NOT_FOUND              | 版本不兼容或未知入口；已有校验                                        | 提示更新或接口错误，不显示保存成功                             |
| UNAUTHENTICATED                                         | 缺可信身份或没有就绪账号；已有门禁，账号查询适配器待实现              | 引导登录，保留输入                                             |
| ACCOUNT_DISABLED                                        | 内部账号不是 active；已有门禁，实际账号查询待实现                     | 停止业务操作                                                   |
| INVALID_INPUT                                           | 保存输入格式错误已有校验；新建窗口、查询/删除白名单及正版本校验待实现 | 指明日期、字段或版本问题，保留输入                             |
| CONFLICT                                                | 同日竞争、版本过期、同 ID 不同输入或旧回执失效；拟约定，未实现        | 不静默覆盖；保留输入并重读                                     |
| NOT_IMPLEMENTED                                         | 当前账号适配器或记录模块占位；已有行为                                | 明确尚未保存或修改数据                                         |
| INTERNAL_ERROR                                          | 非预期服务端失败；已有外层兜底                                        | 不暴露平台异常或正文；保留原请求，结果未知时先确认或重试原操作 |
| CLOUD_NOT_CONFIGURED / NETWORK_ERROR / INVALID_RESPONSE | 客户端环境、传输或响应匹配失败；已有封装                              | 保留输入；结果不确定时复用原请求，不能假定未写入               |

错误按既有外层校验 → 可信账号门禁 → 业务校验/处理的顺序返回；文档中的业务错误样例默认可信 active 账号已解析，不代表当前默认适配器会先返回业务错误。`CONFLICT` 的不同原因先用不含私人数据的 `message` 说明，不新增错误码。本稿中的新业务错误文案是草稿，页面不得依赖文案分支。

## 7. 合成请求与结果样例
