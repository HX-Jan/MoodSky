## 2. 两个需要分别处理的问题

一是至少一个云端场景未通过，真正原因仍未知。二是现有函数只保存批次状态，逐项结果仅通过直接响应返回；工具提前结束等待后，无法通过现有 inspect 取回报告。这两个问题不能混为“云函数超时”，也不能认为加长工具等待或保存报告就会修复失败断言。

当前源码最后用一次批次文档 update 保存 completed/failed；报告没有保存。最小留存提案是在同一次 update 中保存状态和安全报告，再由 inspect 只读返回可用报告。这样，未来完成到这次 update 的实验，即使直接响应未取得，也可以再次只读查看结果。

它不能为旧批次补造当时没有保存的报告；不能保证在最终 update 之前被终止的实验已有报告。旧批次读取应明确 reportAvailable:false，而不是根据数量合成 passed。当前 60 秒运行限制保持原样，本提案不扩大运行时或放宽断言。
