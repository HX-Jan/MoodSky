## 2. 可重复清理的定义

「可重复执行」= 同一清理动作执行 N 次与执行 1 次结果一致：

- 删除已不存在的行不报错，返回「已清理」；
- 不使用「先查总数再删」作为唯一依据（中途失败会导致状态错乱）；
- 每次执行产出可核对结果（已清理行数），供 `cleanup_jobs.progress` 与进度回执使用；
- 失败必须如实返回失败与原因，不得标为 `completed`。

拟定形式（与 Xiang Yu 的清单一致）：按服务端 ownerId 分批删除。分页大小、超时与检查点语义由 Xiang Yu 的清理执行器定义；**按 ownerId 幂等可重入**是尚未实现的验收目标，不能仅凭 remove 调用形式宣称已保证。

## 3. 共用账号校验（供导出与清理调用）

导出与领取需要「本人身份 + 账号状态」校验，清理执行需要「任务归属」校验。本人提供的服务端能力 **[待确认命名]**：

```
resolveAccountStatus(trustedContext) -> { accountId, status }   // 供导出领取校验
assertActiveAccount(actor)           -> void                    // 供私人业务前置校验
```

约束：

1. 输入只来自**可信上下文**，绝不接收客户端传入的 `accountId`（`validation.js` 已把该类字段列为保留字段并直接拒绝）；
2. 账号 `disabled`、凭证过期、或相关记录被删除后，**旧导出按规则失效**（F22 验收口径），领取时必须重新检查；
3. 校验结果不回显给客户端；客户端无法通过入参影响判定；
4. `export_jobs.ownerId` 由服务端写入，来源于 `actor.accountId`。

## 4. 导出内容边界

- 导出包含：本人任务历史（`task_history`）与偏好（`preferences`）。

- `task_history` 导出的是 `taskId` 快照；**模板标题是否随导出一并固化仍待确认**（模板改名后导出可读性会受影响）。
- 导出文件生成、格式化、领取与到期由 Xiang Yu 主责；本人只提供上表查询能力与账号校验。
